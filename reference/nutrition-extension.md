# `src/nutrition-extension.ts` — design rationale, history, and citations

Full prose moved out of the source file's comments, preserved verbatim and organized by symbol in source order. The source file itself now carries only short "what it does" descriptions plus a pointer here.

## File-level

`ROADMAP.md` Phase 6, `nutrition-extension.ts` as planned — the one file in `CLAUDE.md`'s module-layout table that kept its originally-planned name, because nothing forced a divergence the way `heat-source.ts`/`place.ts`/`schema-org.ts`/etc. diverged. Builds directly on `Entity.composition.nutrientsPer100g`, already present on every entity that has a citable figure — this module doesn't duplicate that, it adds a second, genuinely different fact: not "how nutritious is this food" but "what does this food count as, and how much of it, toward a specific USDA regulatory meal-pattern requirement."

**Deliberately NOT a field on `EntitySchema`.** This is the direct, load-bearing answer to a real, user-supplied ticket ("Ticket 1: Purge External Identifiers and USDA Models from Core Schema," checked 2026-08-17, `ROADMAP.md` Phase 6) that asked — ahead of this schema existing at all — for `mealPatternContribution` to be kept out of the core entity schema and modeled as a pluggable extension instead, specifically to avoid bloating `EntitySchema` with a fact that's only relevant to one regulatory context (a federally-funded school-meal program) among many possible uses of this repo's data. That ticket found nothing to remove (the field had never been added), but its own stated intent — extension, not core-schema bloat — is exactly what this module now honors when the real thing finally gets built: a separate schema, a separate `data/meal-pattern-contributions/*.json` directory (one file per entity that has a citable figure, keyed by `Entity.id` — same shape `registry.ts`'s `loadDir` already expects for `ccps`/`heat-sources`), and a separate `registry.ts` loader (`loadMealPatternContributions`) — not a new optional field threaded through `EntitySchema`/`data/entities/*.json` itself.

**Scope, named honestly**: this module covers the National School Lunch Program (NSLP)/Child and Adult Care Food Program (CACFP) meal pattern under 7 CFR 210.10 — the specific, well-documented federal regulatory program `CLAUDE_DEV_CTX.md`'s own sketch names ("school lunch nutritional ounce/cup equivalents"). It does not attempt USDA's separate `MyPlate` consumer-guidance cup/ounce equivalents (a related but distinct system with its own crediting rules), FDA nutrition-facts-label serving sizes, or any other country's school-meal regulation. Real, cited data is attached to only 12 of this repo's ~42 entities as of 2026-08-19 (egg, milk, potato, onion, garlic, flour, oil, sunflower_oil, salt, kosher_salt, flaky_salt, butter) — additive, opt-in coverage, the same "field defaults to nothing, not every entity gets one" precedent `invalidTransitions`/`storageLifeByState`/`domainFacts` already established. Composite entities (dough, tortilla_mixture, alioli, ...) are deliberately NOT given a contribution here — crediting a composite proportionally by its components' own contributions would need a real per-component mass/proportion calculation this repo has no cited methodology for; guessing one would be a fabricated shortcut, not a cited fact, so it's left unaudited rather than invented.

## `MealPatternComponentSchema`

The five real NSLP/CACFP food components (7 CFR 210.10) plus `not_creditable` — a real, audited "this doesn't count toward any of them" fact (fats/oils, seasonings), not a value silently left out of the enum. Naming it as its own enum member matters for the same reason this repo's `hazards: []` / `criticalControlPointsByAction: {}` are treated as audited-empty rather than unfilled elsewhere: a caller can't otherwise tell "checked, doesn't credit" from "never looked at."

## `VegetableSubgroupSchema`

7 CFR 210.10(c)(2)(iii)'s five required subgroups (dark green, red/orange, beans/peas/legumes, starchy, other) plus "additional" (any subgroup, filling the remaining weekly requirement once the five minimums are met) — each subgroup has its own separate weekly minimum in the regulation's Chart 1B, not interchangeable with the vegetable component's overall total.

## `UsdaMealPatternContributionSchema`

A discriminated union on `component`, deliberately mirroring `ingredient.ts`'s own `QuantitySchema` in shape (a closed set of kinds, each with the fields that specific kind actually needs) rather than one loose object with every possible field optional. Three genuinely different crediting BASES are real, not an arbitrary implementation choice: `meat_meat_alternate` credits by discrete count (a whole egg), `milk`/`fruit`/`vegetable` credit by as-served volume (a cup), and `grains` credits by mass of creditable ingredient (grams of flour) — conflating these into one generic "amount per unit X" field would hide a real semantic difference the crediting math (`creditedAmount`) has to respect exactly.

`grains`' `creditableGramsPerOzEq` is deliberately scoped to one crediting rate (16g/oz eq, the Food Buying Guide's "Groups A-G" rate for baked, flour-based products) rather than modeling the full grains-crediting system, which also has a distinct 28g/oz eq rate for "Groups H-I" (cereal/grain-based desserts) — named as a real, deliberate limit rather than silently wrong for a food this repo doesn't currently model in that second category anyway (this repo's only grain-component entity, `flour.json`, is only ever baked into `simple_flatbread.json`, a Group A-G product).

## `MealPatternContributionFileSchema`

`id` is the `Entity.id` this file describes, not a separately-invented id the way `ccps`/`heat-sources` have their own semantic ids (`egg_pasteurization_raw`, `gas`) that entities reference BY id from a different field. The relationship here is naturally one-to-one (does this entity have a meal-pattern contribution, and what is it), so the file's own `id` doing double duty as the join key is the more direct, less redundant shape — `registry.ts`'s existing generic `loadDir<T extends {id: string}>` needed no changes to support it.

## `creditedAmount`

Mechanical and conservative on purpose: it computes a credited amount ONLY when the `Quantity`'s unit is exactly the one the crediting rate is defined against (`count` for meat/meat-alternate, `cup` for milk/fruit/vegetable, `g`/`kg` for grains) — it never converts between units (no mL/tsp/tbsp-to-cup, no count-to-mass) even though `QuantitySchema` has other units that could plausibly be converted. A cup-to-milliliter conversion factor would need its own citation and its own confidence tier the same as every other numeric fact in this repo, and USDA's own meal-pattern crediting guidance explicitly instructs crediting from standard, calibrated measuring cups/spoons — i.e. the "cup" a recipe is authored in is already the same "cup" the meal pattern credits against, so there is genuinely nothing to convert for the units this function DOES support; for the units it doesn't, returning `undefined` (named, not guessed) is more honest than inventing a conversion constant just to always produce a number. `imprecise`/`relative` `Quantity` kinds are excluded for the same reason — a "pinch" or a baker's-percentage ratio has no fixed volume/mass to credit without guessing one.
